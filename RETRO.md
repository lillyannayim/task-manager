## 1. Slash command value

The command that saved me the most prompt-writing effort was `/scaffold-endpoint`, which is the second row of COMMAND_LOG.md. I typed only `/scaffold-endpoint tags POST`, and Claude changed exactly `routes/api.py`, `tests/test_api.py` and a new `services/tags.py` while all 66 tests passed and ruff stayed at 6 errors. If I had written this as an ad-hoc prompt, I would have needed to name all four files, explain that this repo has no `routes/tasks.py` or `schemas/` folder, say that the route must not hold business logic, repeat the import block rule for `routes/api.py`, and list which status code each HTTP method should return in the test. For example, each of my Week 5 subagent prompts in DECOMPOSITION.md needed its own Goal, Context and Constraints written out by hand. However, the command is better for more than saving typing; it also gives me one place to improve. When Claude pointed out that a POST with no JSON body fails inside Flask before it reaches `create_tag`, I added the `request.get_json(silent=True) or {}` constraint to `scaffold-endpoint.md` once, and every future endpoint will get that fix without me having to remember it.

## 2. Hook reliability

During Part B, both vectors got past my hook before I fixed it. For Vector 1, I asked Claude to edit `Utils/errors.py`, and I noticed that it did not use the Edit tool at all; it saw there was no `Utils/` folder and ran `sed -i` on the real `utils/errors.py` through Bash. When I tested the case gap directly by sending the hook an Edit call for `Utils/errors.py`, it returned `exit=0`, so that path would have gotten through as well. For Vector 2, Claude wrote the file to `utils/errors.py.tmp` and then used `mv` to replace the original, which also went through. What surprised me is that Bash was already in my matcher in `settings.json`, so the hook really did run on both commands; the Bash branch just only looked for `rm -rf`, `DROP TABLE` and force-push and never checked file paths. This showed me that "the rule is in settings.json" only means the hook gets called, while "the rule is enforced" depends on whether the code inside the hook checks every way a tool can reach that file. Furthermore, in the baseline test and in the first Vector 2 attempt, Claude stopped on its own and said it would not work around the block, but that was its judgment and not enforcement, since the very next prompt that asked for bash got through.

## 3. Advisory vs. deterministic

One rule I left advisory in the Do-not-touch section of CLAUDE.md is "Do not reformat or reorder the import block in `routes/api.py`." I did not graduate it because my hook can only protect a whole file by its path, and `/scaffold-endpoint` has to edit `routes/api.py` to add every new route; blocking the file would break the command that saved me the most effort. Considering that the scaffold run in COMMAND_LOG.md added its import on a new line and left the existing imports untouched, the advisory rule is working for now. The rule exists because of Week 5 Session 6, when Claude reformatted an import line beyond what the plan approved. I would graduate it the first time `git diff routes/api.py` after any session shows a removed or changed line among the existing import lines at the top of the file. At that point I would add a content check to `guard_writes.py` that blocks any Edit or MultiEdit on `routes/api.py` whose `old_string` contains `from services.tasks import (` or `from utils.errors import`, since adding a new import line never needs to replace those lines.

## 4. Limits of hooks

A rule I wanted to enforce but could not implement as a PreToolUse hook is the CLAUDE.md convention that every new service function gets a matching test. PreToolUse only sees one tool call before it runs, so when Claude writes `create_tag` to `services/tags.py`, the test does not exist yet, and the hook cannot know whether Claude will write it in the next step. For example, during `/scaffold-endpoint tags POST`, the service file was written before `tests/test_api.py`, so a PreToolUse rule would have blocked correct work in the middle of the task. The right mechanism is a check that runs after Claude is done, such as a Stop hook or a CI step that compares new `def` lines in `git diff services/` against new test names in `tests/`. After researching my own bypass fix, I found a similar limit; my Bash check is still string matching, so a command like `f=utils/err; echo x > ${f}ors.py` gets through because the full path never appears in the command, and a `!` command I type myself never reaches the hook at all. All in all, I learned that PreToolUse is good for blocking a single obviously wrong action, but rules about the end state of the repo belong in a check that looks at the finished diff.
