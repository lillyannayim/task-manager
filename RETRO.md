# Week 5 Retrospective

## 1. Plan Mode value

The clearest case where amending a plan prevented a revert was Session 1 in PLAN_LOG.md. Claude's original plan added a priority field to create_task and the new update_task, but it only gave priority to new tasks, so the three seed tasks in TASKS would not have had the key at all. I amended the plan so that every seed task got "priority": 3 before approving it. I did not realize how important that was until Session 3, when Claude wrote list_tasks with the filter `task["priority"] == priority`. If the seed tasks had no priority key, GET /tasks?priority=3 would have crashed with a KeyError and returned a 500, and I would have had to go back and redo the Session 1 work in services/tasks.py. In the same session, I also stopped the command that appended the update tests and asked for an autouse fixture that restores TASKS, because test_update_task_priority changed task 2 and never put it back. That fixture later became tests/conftest.py in Session 4, so one amendment in Session 1 kept the whole test suite from leaking state for the rest of the project.

## 2. Plan Mode limits

The one case where the output did not match the amended plan was Session 6. I amended the plan for GET /users/{id}/tasks so the ?done filter lived in the route instead of services/, which was a deliberate test against the "no business logic in routes" rule in my CLAUDE.md, and Claude's revised plan accepted the override. The revised plan said to add get_tasks_for_user to the existing services.tasks import line in routes/api.py. However, Claude rewrote that line into a three-line parenthesized import block instead. process_order was kept and ruff still showed the same 6 errors, so nothing broke, but this was a change the plan never mentioned, in the same import block I had protected in Sessions 2 and 3. I also noticed that the revised plan said none of the 6 ruff errors were in routes/api.py, even though two of them were. This tells me that the reliability boundary of Plan Mode is the details the plan does not spell out. Claude followed every rule I wrote down directly, like "do not touch services/" or "run pytest -q last," but when a plan step was vague about formatting, Claude filled the gap with its own habits. The only reason I caught it was reading git diff after the session, which means Plan Mode reduces the need for review but does not replace it.

## 3. Subagent value

The most important boundary to enforce was between SA-2 (services/users.py) and SA-3 (routes/api.py). SA-2's constraint said never to return Flask responses or status codes and to raise NotFoundError or ValidationError instead, and SA-3's constraint said to put no validation in the route and let errors reach handle_app_error. Because both sides were written into the decomposition, SA-3 started immediately with the exact function names from SA-2's hand-off, and its two routes were each only a few lines. If I had let Claude build the whole feature in one session, I think the layers would have blurred. For example, Session 6 showed me that once logic is placed in a route during a session, Claude is willing to keep it there, and in a single long session that kind of decision would carry forward into the tests and later routes. SA-2 also showed the value of a fresh session with a narrow constraint. My CLAUDE.md says every new service function should get a test, but SA-2's constraint said not to touch tests/, so Claude stopped and told me instead of writing tests in the wrong place. In one combined session, it would have just written them, and I would not have had a clean point to check each layer with pytest -q.

## 4. Gap analysis

The rule from Task 2 that I would most want to enforce mechanically is the file boundary in each constraint field, such as SA-3's "Only edit routes/api.py. Do not touch anything in services/, utils/errors.py, or tests/." Claude followed every one of these in Task 2, but I only knew that because I ran git diff --stat after each subagent, and Session 6 showed that small unrequested edits can still slip through when I am not checking closely. A PreToolUse hook that enforces it would read the list of allowed file paths for the current subagent and block any Edit or Write call to a file outside that list, returning an error message that names the file and the subagent's allowed paths.
